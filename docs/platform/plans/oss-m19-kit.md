# Communications extension kit

Status: implementation prepared; maintainer API read pending; development preview.

## Outcome and boundary

Provide an offline, runner-independent communications adapter conformance helper
through the existing platform communications entry. A deliberately incorrect
adapter must fail with an actionable, sanitized finding; its corrected version
must pass from a plain Node consumer script. Map every declared package export's
existing `packageSmokeEvidence` to runnable consumer checks without another
evidence catalogue.

The assigned worker implements this kit under the distribution supervisor.
Local edits and focused checks are authorized. A stabilized public API requires
maintainer reading before signed commits. Native review requires two independent
reviewers after that read. Canonical verification waits for the lead's landing
selection. Submission and merge remain subject to the programme's existing
grant and gates; no release dispatch, publication, credentials, settings, hosted
resources or adopter changes are authorized here.

## Acceptance and proof

- Email transport fixtures discriminate accepted, failed and suppressed outcomes;
  a mismatched result is refused with a bounded fix and recheck instruction.
- Marketing-sync fixtures use the existing contracts and synthetic helper to
  discriminate declared capabilities, refusal before effects, identity binding,
  negative feedback and replay without duplicate effects. Fixture proof does not
  certify the full provider, consent-push lifecycle or live readiness.
- The documented bad/good Node example executes against the packed export in
  the existing isolated cold consumer. Focused tests exercise missing proof,
  malformed results and exceptions without leaking adapter errors.
- The evidence projection derives every row from each package's manifest and
  `release-gates.json`; each row retains its original source witness paths and
  supplies a consumer-local import check, clearly distinguished from behavioural
  conformance and source-suite execution.
- Focused tests, strict published-tree typecheck, structural rules, lint,
  publication/documentation policy and API snapshots precede the read packet.
  Full package/coverage and canonical verification remain required later.

Risk: consumers could mistake fixture or import proof for complete runtime
qualification. Documentation and reports state the exercised boundary and
preserve unknown/live-provider limits. Reuse the existing entries, fixtures and
evidence instead of introducing a registry or CLI.
