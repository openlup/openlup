## Acceptance and proof plan

Risk: exposing an admin read without authority, leaking upstream/request content
in logs, or mistaking capture/absent liveness for delivery/health. Existing typed
handlers, the observed-route boundary and kernel refusal semantics own these
controls; the composition adds no alternative domain engine or grant.

- Execute the retained evaluator through the selected portable composition,
  capture an actual alert, and read useful alert/report projections from it.
- Prove checkOnly causes no alert/ledger writes, repeat/backoff semantics survive,
  and unavailable evidence/sinks cannot be reported as successful delivery.
- Capture correlated logs without raw sensitive details; reject unsafe caller
  correlation values and keep absent liveness/readback unknown.
- Keep existing domain projections, authority and truth boundaries intact;
  no money/order mutation or provider activation follows from diagnostics.

Inspect existing owners and seams, then make the smallest sufficient composition
change. Prefer direct binding of existing mechanisms over another service or
dispatch layer. Placement: reference-application source composes the existing
Platform subpaths; no module algorithm, npm entry or topology trigger is added.
Focused executed proofs must distinguish success from missing
evidence, privacy refusal and failed delivery. Run cheap policy/inventory,
neutrality, structural and redacted secret checks before broad verification.
Freeze inputs, respect the shared host's heavy-stage admission, obtain two fresh
parallel FULL reviews and run canonical verification before authorized delivery.
