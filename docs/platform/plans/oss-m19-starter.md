# Neutral starter application

Status: implementation draft; full-store qualification pending. Runnable-base
evidence is recorded below.

## Outcome and boundary

Compose an independent, unpublished application in `examples/neutral-store/`
using one exact OpenLup npm set. Supply fictional supplement and coffee inputs,
storefront/product/builder/cart/checkout/account/operator pages, localized message
destinations and admitted capability composition through existing public ports.
One typed configuration and three ordinary presentation fragments own
customization. An extraction script creates an independent application repository
with an explicit owned/managed file inventory.

Scope: the starter, its publication rows, adopter-kit pointer, documentation
routing and this record. The bounded execution-inventory addition is one private
starter manifest with no bin or install hooks, its exact executable paths and
its mirrored surface digest. Existing enforcement and all other rows remain
unchanged. No package implementation, root application imports, real payment
provider, live connector, hosted resource or production activation is included.
Accepted native limitations remain visible actions with named refusals. A missing
required store remains a blocker, never an application replacement engine.

- An empty directory becomes an independent repository with no monorepo lookup,
  inherited workspace configuration or imports outside the application.
- One documented command with Docker installs the selected artifacts, migrates
  automatically, seeds a fictional catalogue and serves the app. A real browser

- Every message destination is followed in Polish and English, including valid
  and invalid authentication, review, recovery and unsubscribe grants.

  without a page copy or engine edit. Browser and host use the same application
  validator. A real package upgrade preserves those inputs and fragments.
- Reviews, acquisition, research, partners, disabled risk, market inputs and
  normalized ingest are composed within existing capability limits.
- Accepted unavailable actions display their named refusal without hiding the
  action or inventing a success.

Proof must distinguish real persistence, authority, replay and engine use from a
rendered page. Source tests and sample HTTP responses alone do not establish a
purchase, subscription, migration or upgrade. Required native bindings remain
completion obligations, separate from accepted limitations.

## Execution and risk

Configuration, localization and pages precede persistence integration. Browser
code uses public contracts; server factories stay at the host composition root.
The cart is browser convenience state. `shared/offer.ts` owns one application
validator, while package engines retain quote and durable-effect authority.

Install identified candidate artifacts in a clean directory, then run compiled
feedback, browser/refusal journeys, timed startup and real upgrade preservation.
Apply documentation impact, stabilized reads, independent native review and
final verification before delivery. Preserve pending work and subscription
invariants throughout adoption.

Risks: missing installer/stores; accidental exposure of local demo authority;
confusing a scoped grant with account access; stale cart estimates; overwriting
owned files on upgrade. Keep the host local, authenticate before store access,
revalidate the offer on the host and preserve the ownership inventory.
