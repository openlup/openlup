The first six fixture files retain the exact whole bytes bound in
[`qualifiedInstallations`](../../../../../../config/reviewed-platform-forwards.json).
The sixth runtime-completion fixture equals its separately introduced canonical
SQL, bound by the unchanged sixth prior-approval row.
They are not an installation chain, a package SQL export or a migration source.
Reader preparation landed before this sixth approval row, which landed before
active SQL. All six approval rows and the canonical manifest's legacy 88-unit
selection and complete F90 prefix remain unchanged; the completion is unit 91
of the qualified selection. Trusted admission parses a changed registry
using main's reader before its no-SQL return, so reader support must land first.
At that checkpoint the exact sixth approval landed before the SQL feature
introduced the identical file and appended its selected row; under the current
co-location rule in `docs/platform/DATA_AND_MIGRATIONS.md`, new approvals may
land with their SQL.
Observed installation hashes cannot replace prior source approval.

The seventh fixture binds the qualified owner-path forward's exact nine
definitions. Its reviewed file and function hashes were approved before the
identical active SQL was introduced as qualified unit 92.

Five additional `qa_` files remain inert restricted-bootstrap candidates. This
separate control-only checkpoint adds their exact whole-byte approvals at
positions 8–12; no `qa_` SQL or schema-3 plan enters the active migration
catalogue. The nine owner-executed definitions shared with the qualified
owner-path forward carry its pinned name-resolution attributes in these bytes;
the two retained-import definers already use the same pinned search path.
An actual PostgreSQL 16 parse-and-apply attempt found a syntax error in the
approved actor bytes. Those twelve approval rows and their fixtures stay
unchanged. Four new inert `qb_` fixtures parenthesize the CASE sums in the
actor, acquisition, runtime and import units. The reader accepts their paths
only as an atomic positions 13–16 append. This separate checkpoint approves
their exact bytes after a two-mode disposable parse-and-apply witness. They
are not active installation files in this checkpoint. The restricted generation
will select the `qa_` baseline and four `qb_` replacements, then reuse the
issued completion tail without the qualified owner-path forward. See the
[restricted-bootstrap task](../../../../../../docs/platform/plans/oss-m14-restricted-bootstrap.md).

The `q2_20261103200000_runtime_lock_and_conflict_completion.sql` fixture binds
the exact approved bytes at the seventeenth position: one shared tail for both
qualified plans. It lets the restricted runtime take three existing row locks
without admitting an actual update. It also lets the runtime read only the two
arbiter columns that an existing conflict target requires, and only the client
column that operator lead absorption counts. Reader support and this approval
landed separately; both qualified plans now select the byte-identical active
SQL.

The [migration owner](../../../../../../packages/core/docs/guide/upgrade/database-migrations.md#select-the-complete-catalogue)
