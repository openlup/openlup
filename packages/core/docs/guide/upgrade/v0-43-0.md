# Upgrading to 0.43.0

Upgrade from the complete 0.42.0 package set using the [upgrade procedure](README.md).
This development-preview minor set adds native fulfillment APIs and seven SQL
forwards, payment provider profiles and release-artifact qualification tooling.
Core's shared fulfillment status-map JSON drops provider trace columns while
preserving neutral status/customer-step results; Outbox republishes unchanged
runtime, exports and SQL. Pin every selected `@openlup/*` package to 0.43.0
together. Package installation and imports apply no SQL and activate no provider.

## Apply the native schema migrations

Apply the complete selected catalogue, including every predecessor and these
ordered forwards, before composing the updated ports:

| Registry slot | Migration | Purpose |
| --- | --- | --- |
| 135 | `20261119200000_communication_event_prepare_erasure.sql` | Prepare the receipts relation lock before privacy subject locks. |
| 136 | `20261120100000_fulfillment_intake_channel.sql` | Record the selected push/poll dispatch acknowledgement channel. |
| 137 | `20261120110000_fulfillment_dispatch_outcomes.sql` | Native creation, operator attempts, dispatch admission and durable diagnostics. |
| 138 | `20261120120000_fulfillment_provider_intake.sql` | Durable provider observations, ingress correlation and reconciliation. |
| 139 | `20261120130000_fulfillment_alignment_arrival_chronology.sql` | Replacement preparation and arrival chronology for customer alignment. |
| 140 | `20261121090000_payment_provider_profiles.sql` | Replace ten effective payment-policy functions with declarative profile selection. |
| 141 | `20261121100000_order_delivery_contact_correction.sql` | Resolve, correct, capture, export and erase native delivery contacts. |

Follow [Upgrade the database](database-migrations.md). Retain the installation
selection that owns your history, construct `createPlatformPostgresMigrationRunner`
from `@openlup/platform/migrations`, inspect `status()`, review
`apply({ dryRun: true })`, explicitly call `apply()`, then confirm there are no
pending paths. The runner applies only the pending suffix of an exact matching
prefix. Preserve every applied SQL byte and ledger identity. Module descriptors
are sparse projections, not standalone installation chains. An application with
its own chain must prepare compatible forwards against its actual schema and
history rather than overlaying an unrelated baseline.

## Compose fulfillment in the application

Use the neutral contracts at `@openlup/platform/fulfillment/contracts`, services
at `@openlup/platform/fulfillment` and native factories at
`@openlup/platform/fulfillment/native`. Follow the
[installed-store composition](../how-to/build/fulfillment.md#compose-an-installed-store-end-to-end):
select an adapter and capabilities, supply a capability-local transaction lane,
authorization, service selection and schema metadata, and explicitly enable the
native binding. Select `nativeDispatch: { portKey, providerRef }` or retain your
own authoritative reader and candidate listing. Supply the adapter's pure
`shadowCommandFingerprint`; declarations and constructors mount no routes,
workers or schedules.

Create the local paid-order obligation before dispatch. Compose authenticated
intake and leased reconciliation with recorded dispatch commitments, exact
parcel reservations, the adapter's outbound order-identity mapping and the job
ledger. Retain original provider occurrence bytes and first receipt separately.
Provider identity resolves first; conflicting fallback associations refuse.
Recorded attempts preserve exact replay; uncertain acceptance needs verified
readback or authorized recovery before any later execution.

Bind the authorized label, handoff, tracking and contact-correction handlers.
Contact correction requires both the PostgreSQL digest and revision, the native
response schemas and the updated privacy contributor. Bind
`createPostgresCustomerAlignmentRowsReader` to `readFulfillmentDelay`, authorize
customer IDs and supply current schedules. Replacement dispatch uses its own
parcel identity and adapter-owned numbering. Only actual customer arrival can
settle alignment; a superseded predecessor is no longer outstanding, while an
undelivered replacement remains outstanding. The monotonic clamp extends a late
cycle once, never moves it earlier and never stacks deliveries.

Use `@openlup/platform/fulfillment/testing` for offline adapter certification.
Existing one-argument calls retain baseline mode. Full mode needs independent
expectations, typed success/failure and refusal witnesses against the captured
immutable adapter and real scripted transport log. The detailed migration notes
below describe the fixture changes. The installed-package PostgreSQL proof uses
a scripted provider; it supplies no live carrier qualification.

## Declare native payment provider profiles

The profile forward replaces exactly ten effective policy functions and retains
their privileges, including the sealed interactive body. Historical migrations,
stored provider identities, evidence and receipts stay unchanged. Both reference
profiles preserve their existing validation order, refusal, claims, refund and
replay rules. Arbitrary admitted providers retain generic fallback behavior;
claims and reopening are opt-in. A third provider needs an explicit profile
declaration plus its protocol adapter; a new protocol or money/retry semantic
still needs its own implementation. There is no mutable policy registry or
per-command profile JSON. Optional host-selected execution flow labels are
additive; omission preserves the existing composition.

The portable composition covers the reference card provider only. See
[provider composition](../how-to/extend/provider-adapters.md) and the migration
notes below before changing an existing binding.

## Qualification changes visible to an adopter

Release tooling can extract an exact published package set with verified tag,
manifest and lock identities, then install it independently with exact package
integrities and provenance for every package. The qualification receipt and
package-set bill of materials bind those artifacts. Separate checks exercise an
interrupted adjacent-set application-file upgrade and released-pair schema
compatibility, preserving owned application files and the subscription clamp.
The schema check uses the selected qualified PostgreSQL 16 profile; it supplies
no general database rollback or hosted-service guarantee.

When explicitly published, a qualified starter image is bound to that exact
artifact set, application extraction, dependency inventories and verified image
provenance; its canary exercises the actual archive before publication. These
are bounded artifact and sandbox-journey checks, not live payment or carrier
qualification, a complete store outcome or a stable support promise. This
preparation itself claims no executed qualification for 0.43.0. See
[verify published packages](../how-to/operate/verify-published-packages.md) and
[distribution evidence](https://github.com/openlup/openlup/blob/openlup-core-v1.4.0/docs/platform/DISTRIBUTION_EVIDENCE.md).

## Known limits

Provider and carrier proof is limited to fake clients, scripted adapters and offline fixtures; no live provider or carrier qualification is claimed. The starter still selects sandbox payments. The native payment rail supports the two reference providers through declarative profiles; a third provider needs a declaration plus its adapter. The supplied portable payment composition covers the reference card provider only; the second reference provider has no supplied portable composition. The included warehouse adapter is a reference example. Imports, declarations, package installation and offline certification activate no integration.

Fulfillment retains local reservations and local finished-picking consumption; provider-held reservations, provider-managed consumption, independent splits, standalone pickup-point/locker execution, native label create/void and provider-side cancellation remain unsupported. Labels are PDF only; reference-adapter label reads remain host-owned. Courier pickup has no provider-reaching port and declared support cannot earn full certification. Snapshot-only stock has no movements. Saved preferences require carrier/service strings even when native provider-selected parcels allow nulls. Native overview data requires a host reader.

Historical contacts, reservations, modes, acceptance proofs and arrival facts are not backfilled. Failed or uncertain dispatch and a lost replacement acknowledgement never authorize blind resubmission. Fulfilled parents need an authorized host workflow for replacement dispatch. Replacement creation/dispatch never confirm arrival: record actual delivery; an undelivered replacement remains outstanding. Delivered observations without admitted tracking references retain status evidence but cannot record arrival or alignment. The monotonic clamp never moves a cycle earlier or stacks deliveries.

Intake uses sequential page numbers, not opaque cursors; polling-only providers refuse webhook intake. Empty collections prove no absence. Human holds, terminal provider exceptions and evidence without usable chronology require manual handling. Native reads refuse missing destination/line snapshots. Replaying incomplete webhook transport metadata may replace polling-enriched nullable reference fields. Resolve missing or conflicting historical associations and evidence through authorized recovery; no inferred parcel, chronology or stock is supplied.

Offline certification checks honestly built fixtures and contract results; deliberate accessor, proxy or overridden-intrinsic manipulation to defeat the caller's own certification is outside its threat model. It is not an attestation of durable host behavior. Absence auto-reopen stays off by default and later dispatch requires explicit due-reopen consumption. Refund creation remains separate; refund evidence does not pause or cancel subscription service. Experimental services remain inert until explicitly composed.

Read the [fulfillment execution limits](../reference/limits.md#fulfillment-execution-limits)
and [payment composition boundaries](../reference/limits.md#purchase-composition-boundaries)
for the named refusals and authorized manual paths.
