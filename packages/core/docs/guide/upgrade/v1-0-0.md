# Upgrading to 1.0.0

Upgrade from the complete 0.43.0 package set using the [upgrade procedure](README.md).
This is the first stable set and a major transition from 0.x. Pin every selected
`@openlup/*` package to 1.0.0 together. Core adds catalogue primitives and installed
lookup improvements; Outbox republishes unchanged runtime, exports and SQL;
Platform adds experimental catalogue tools, nine native SQL forwards and optional
subscription admission. Imports and installation apply no SQL or integration activation.

## Stable commitments

The [stability reference](../reference/stability.md#public-api) owns SemVer from
1.0.0. The [maturity table](../reference/maturity.md) identifies stable,
experimental and testing subpaths; `@experimental` symbols within stable subpaths
are excluded from the stable promise. Status, event, reason, command and capability
unions and literal sets are open: additions are minor; keep a default branch for
unknown values. Removal, renaming or narrowing requires a major release. Within
1.x, schema changes are additive expand/backfill; contraction requires a major.
The latest 1.x minor receives fixes including security fixes, with no LTS or
maintenance branches. Installation support is limited to the npm starter,
PostgreSQL and the qualified image under the linked support policy; release
evidence is retained for one year. Consumer evidence is first-party: a demo store
from npm and a production deployment. This preparation claims no executed exact
1.0.0 artifact qualification; require the release's own retained evidence.

## Apply the native schema migrations

Apply the complete selected catalogue, including every predecessor and these
ordered forwards, before using the new readers or explicitly composed tools:

| 143 | `20261122110000_catalog_quantities.sql` | Nullable physical quantities on live SKUs; data conversion is a separate explicit backfill. |
| 144 | `20261122120000_catalog_attributes.sql` | Nullable product/SKU attribute objects and the single rebuildable SKU-keyed projection. |
| 145 | `20261122130000_catalog_variant_axes.sql` | Nullable axes, option values, canonical identity bytes and active-combination uniqueness. |
| 146 | `20261122140000_subscription_price_policy_close_digest.sql` | Preserve the original policy digest across a one-time revision close with `closed_from_open`. |
| 147 | `20261122150000_catalog_drafts_v2.sql` | Explicit v2 draft admission and resume on the four existing retained draft relations. |
| 148 | `20261122160000_catalog_drafts_v3.sql` | Expand draft admission to v3 publication inputs and ordered operations without executing them. |

| 150 | `20261122180000_catalog_base_price_writer.sql` | Explicit immediate base-price writes and authoritative immutable command receipts. |

Follow [Upgrade the database](database-migrations.md). Retain the installation
selection that owns your history and construct `createPlatformPostgresMigrationRunner`
from `@openlup/platform/migrations`. Inspect `status()`, review
`apply({ dryRun: true })`, explicitly call `apply()`, then confirm no pending paths.
The runner applies only the pending suffix of an exact matching prefix. Preserve
all applied SQL bytes and ledger identities. Module descriptors are sparse
projections, not independent installation chains. An application-owned chain must
prepare compatible forwards against its actual schema/history rather than overlaying
an unrelated baseline. These catalogue additions have no managed-rail twin in this set.

After schema installation, explicitly call `installCatalogDefinitions(installExecutor, pack)`
with the native migration-owner executor if adopting definitions. Existing products
remain NULL-bound legacy; no mapping is inferred. Keep old definition versions in
code while products reference them. To convert legacy net content, separately drain
`backfillCatalogNetContent(installExecutor, { batchSize })` with a positive integer
batch size and migration-owner executor. It converts positive legacy grams exactly
to mass, scale 0 and `openlup:g`, preserves zero as unknown, never overwrites existing
net content and never infers gross mass. Interrupted batches resume; replay is a no-op.
The migration itself does not backfill. Runtime roles receive no installer/backfill authority.

Old readers ignore the nullable expansions. Existing non-null legacy quantity
columns and readers remain in use; new catalogue serving, publication and host
migration wiring are not supplied. Attribute objects retain NULL until explicitly
provided. They have independent PostgreSQL-rendered text ceilings of 1,048,576 bytes;
canonical JSON safety limits measure different bytes. The projection remains
owner-only and rebuildable, with no runtime grants. Variant fields remain NULL;
no empty combination, legacy digest or inferred identity is manufactured.

## Adopt experimental catalogue tools explicitly

All new catalogue declarations since 0.43.0 carry `@experimental`; established
catalogue readers keep their contracts. The package changelogs preserve the original
fragments verbatim, including former 0.44.0 targets and intermediate checker scopes.
Those targets are superseded by this 1.0.0 set. The final interfaces described here
include the later JSON-only checker integration.

Core's `catalog` entry adds exact decimal-string/BigInt quantities, canonical units,
comparison and declared-unit conversion. Inexact canonical values refuse without
rounding. Existing identifier schemas are unchanged. The experimental pricing
helpers `cataloguePositionNetFromGross` and `allocateCatalogueDiscountedGrossTotals`
preserve integer included-VAT rounding and largest-remainder allocation, with ties
resolved by input position. Compose them with validated money in one currency and
preserve position order. Native integer-conversion errors and refusal messages remain;
existing quote arithmetic and independent invoice verification are unchanged.

Platform's `catalog` and `catalog/contracts` entries add readonly pack descriptors,
typed drafts, declarative metadata, structured definition issues and server-derived
definition/manifest digests. Closed authoring shapes and literal reference keys
remain significant. Existing v1 canonical command and receipt bytes are unchanged;
v1 drafts do not admit attribute values. Parse readonly authored drafts through
`catalogDraftPayloadSchema.parse` before assigning mutable v1 DTOs. The runtime
`CATALOG_CONFORMANCE_RULES` record is at `@openlup/platform/catalog`; contracts export
its codes and rule shapes as types only. Definition errors retain
`invalid_catalog_type_definition` and add the first structured issue.

Attribute validation uses an injected allowlisted batch reference resolver;
malformed values refuse, while missing required values/locales are publication
readiness issues. `attribute_storage_too_large` identifies the product/SKU owner.
Each projected text slot fits 2,048 UTF-8 bytes, including complete localized maps
and list scalars, regardless of facet/filter flags; otherwise
`attribute_projection_text_too_large` refuses before SQL. This conservative index
budget is scoped to the qualified 8 KiB-page PostgreSQL profile. Signed decimals
remain strings; trusted writers must check exact numbers before PostgreSQL numeric
coercion. Pure projection preparation supplies no writer or serving switch.

`canonicalizeCatalogCombinationV2` derives versioned identity bytes and SHA-256
from installed definitions and complete options. Labels and display order are not
identity. Padded quantity coefficients up to 52 input digits normalize through exact
Core arithmetic; the v1 wire schema keeps its 40-digit coefficient ceiling.
`validateCatalogCombinationChangesV2` preserves omitted SKUs/withdrawals and requires
a new SKU for an existing mapped identity change. Handle
`combination_identity_integrity_failed` for inconsistent authoritative options or
colliding derived digests; incoming mapped changes still report
`sku_identity_change_requires_new_sku`. The earlier `combination_digest_collision`
code remains exported. The 10,000-SKU payload bound is separate from configured
product capacity (default 50,000); no combinations are enumerated. A future publisher
must authorize, lock, validate retained facts, enforce incremental capacity and
record immutable history. These helpers supply no publisher or capability activation.

## Choose versioned draft readers before authoring

Use `createPostgresCatalogDraftStoreV2` and `createCatalogDraftHandlerV2` explicitly
for v2 payloads/commands. Original factories retain v1 admission and exact canonical
bytes, fingerprints and receipts. `CatalogDraftStored*` is the explicit v1/v2 union.
v2 adds typed attributes, publication-readiness checks, resume and complete immediate
positive gross one-time/minimum-one base-price commands. Expected entry ID and
amount are wholly null or wholly set; a zero new amount refuses. Saving incomplete
drafts reports readiness issues and performs no price writes. Resume copies an
abandoned payload into an open revision under retained reservations; earlier
abandonment receipts still replay, and legacy revise on an abandoned head refuses.

For v3, explicitly select `createPostgresCatalogDraftStoreV3` and
`createCatalogDraftHandlerV3` before authoring. `CatalogDraftPublicationStored*`
is the additive v1/v2/v3 union. v3 freezes ordered operations, eligibility,
provenance/media claims, shared-content envelopes and derived SKU facts. The
installed validators own opaque content; input claims establish no authority or
external readiness. Saving executes no operation. v3 retains v2's positive,
immediate one-time/minimum-one price boundary, with no scheduling, tier or zero-price
extension. Unknown versions refuse; older versions' bytes are not reinterpreted.

`createCatalogCandidateService` prepares read-only previews through authorized
injected readers. Its v1 reference resolves immutable revisions, checks the whole
head/document digest, installed/composed definitions and expected publication
identity, then hashes canonical evidence and operations. `compareCandidate` verifies
the supplied head/digest; missing price validation blocks price-bearing drafts.
Publication must reconstruct and refuse issues inside its own transaction. No
candidate table/cache, publication binding or publisher constructor is added.

Stop v2/v3 authoring before rolling readers back; old latest-record readers refuse
newer records. Retain a compatible reader for stored v2/v3 history. The four draft
relations retain their transfer order, privacy classification and authoritative
history, with no backfill or new relation. No live catalogue, price, subscription,
order or delivery fact changes merely by saving a draft.

## Compose the experimental base-price writer

After applying the complete native catalogue through position 150, explicitly
compose `createCatalogPriceSetupHandler` and `createPostgresCatalogPriceSetupStore`
from `@openlup/platform/pricing`. These new contracts, schemas, canonical command
serialization, handler/store ports and factories are `@experimental`. Bind the
store to the same verified human administrator session as the handler authorizer;
imports and installation activate no capability. The managed rail has no twin.

The version 1 command preserves the v2/v3 draft price-operation grammar and exact
canonical bytes: immediate positive gross one-time price, minimum quantity one,
and wholly-null or wholly-set expected entry ID and amount. Later context,
scheduling and list lifecycle require a new command version. SQL derives the actor,
serializes the receipt before the price context, compares the expected base and
atomically closes/inserts at one statement instant. Preview/apply/readback results
are validated. Old price readers keep reading ordinary price entries; the writer
changes no agreed subscription money or schedule.

Readiness requires native financial, agreement and audited cohort evidence.
Missing proof hard-refuses independently of ordinary readiness reasons. The
existing global reason-membership aggregation limit remains: a second invalid SKU
may be hidden by an already present aggregate price-shape reason. Preserve the
catalogue receipt relation's exact fingerprints, actor metadata and responses with
price history during transfer; it is authoritative data, with no customer foreign
key or client absorption rule. Rollback means unbinding callers while retaining
history and receipts. Correct a price with a later expected-base command; do not
delete evidence or downgrade the live database.

## Preserve policy and acquisition evidence

Apply schema first, then the updated policy reader. The optional
`SubscriptionPricePolicyRevision.closedFromOpen` marker preserves the original
digest tuple while serving the shortened half-open window. Legacy inputs keep
canonical bytes. Already-shortened legacy rows that cannot verify refuse with
`subscription_price_policy_original_tuple_unverified`; no backfill guesses their
original tuple. After a close, code rollback must keep the new verifier: older
readers refuse newly closed revisions. Keep schema, rows and retained history.
This repair supplies no closing command, scheduler or capability activation.

Offer-policy readiness records the existing subscription cohort's legacy policy
pair and default-false fixture marker; future ordinary inserts default to pending
acquisition. Installation records immutable marking-time count, membership
fingerprint and database time, but captures no baseline. Audit the complete legacy
non-fixture cohort, including paused/cancelled rows, before explicitly invoking
`commerce_capture_offer_policy_v2_legacy_baseline()` through the service SQL boundary.
Capture is parameterless and inserts once; replay returns the original audit.
A zero audit requires genuine empty marking provenance; an originally populated
marking becoming empty still refuses. Never reset a baseline to make a comparison
pass. The experimental base-price writer runs read-only input checks before and after its
provisional prices in the same transaction, propagates hard refusals and retains
ordinary acquisition reasons and governing purchase-order provenance. Transfer
preserves marking/baseline bytes, reconciling only a pristine target marking row.
The host explicitly composes that writer; it reprices or reschedules no agreement.

## Update host admission and installed diagnostics

Subscription editor hosts may compose the optional effect-free full-result
admission callback on classic, exact and sized ports. Supply nominal and effective
cadence separately, before pricing/writes including frozen-price edits. Completed
receipt replay precedes mutable admission/limits; fingerprint conflicts refuse.
Omitting the callback preserves behavior. Validate resulting dates in the host.
Checkout, quote, recovery and account cadence DTOs now use PostgreSQL integer
representation bounds; historical generic SQL bundle/lifecycle paths keep their
90-day guards. Starter offer derivation and activation remain separate.

Optional `ReadinessInput.catalogRegistry` and `CatalogRegistryObservation` let a
host provide observed catalogue bindings. Missing/different installed versions
report `registry_missing_referenced_version`; incomplete row visibility or a NULL
installed digest yields `unknown`. The observer needs SELECT on both definition
tables with row security inactive; hidden rows do not prove readiness. Compose
`createCatalogDefinitionWriteGuard` explicitly; no boot hook, installer or existing
store binding is added. Absence of the observation preserves existing behavior.

Installed context lookup resolves reachable declared packages and required Core
through Node's npm lookup, including workspace hoisting/links, and checks versions
against the owning npm lock. Application scans remain application-only; declaration
hits are unverified public-import leads. Inspect installed exports/examples rather
than treating a declaration occurrence as import proof. MCP reads accept only the
selected package's exact returned path with bounded ordinary-file/realpath checks;
Node package self-references refuse instead of presenting checkout code as installed.

## Use JSON-only offline catalogue checks

`@openlup/platform/catalog/testing` is a new Node-only test-support subpath. Use
`await runCatalogExtensionConformance(JSON.stringify(subjectData))` or
`openlup catalogue check --packs ./owned/catalogue.json --json`. The supplied file is
JSON text and is never imported; the installed skeleton is one static JSON fixture.
Earlier module subjects, executable skeletons and callbacks are superseded. Replace
refusal callbacks with `observedCode`/`zeroEffects`, reference ports with resolution
rows and retained identity bytes with options. Omit `validateContent`: requested
application content validation is unavailable (exit 2).

The final checker integrates definitions, exact quantities, v1 drafts, attribute
validation/projection and v2 combination fixtures, with deterministic findings and
five CLI exits. It checks malformed type references, own-string capability keys and
positive bounded pack versions through existing owners. Reference/refusal observations
never invoke caller code; fixture-derived identities prove no persisted history.
Only explicitly admitted owner input errors become input refusals (1); other owner
exceptions reject directly and become CLI 74 with raw errors withheld. Default
failure is 74; only tagged JSON parsing yields 64. Integrity codes are not input
refusals. Taxonomy, tax, profile and promotion semantics remain pending. An offline
PASS supplies no database, installation, publication, host wiring or capability proof.
See [catalogue extension recipes](../how-to/extend/catalogue-extension.md).

The fulfillment conformance diagnostic now explains that
`prepare(providerRef: null)` must return `selection_required` before I/O; the
expected refusal and zero-I/O obligation are unchanged. API snapshot updates can
use validated package fragments as well as the legacy changed-changelog route;
that contributor admission change adds no runtime contract.

## Rollback and qualification limits

Reverting application files does not undo SQL or durable effects. The existing
released-pair qualification proves only its recorded adjacent pair, selected
PostgreSQL 16 profile and retained read/write/replay and subscription-clamp
assertions on the unchanged expanded schema. It does not prove a general rollback,
adjacent-pair backfill or contraction. Require exact 1.0.0 artifacts and their own
qualification evidence before treating them as qualified. New v2/v3 history and
closed policy revisions have the reader limits above. Leave additive storage,
converted content, immutable install history and offer-policy audit evidence intact.

Authoritative product/SKU fields remain in their existing retained transfer order;
managed-to-native mapping fills only absent new fields with NULL and preserves
supplied values and other refusals. The attribute projection is rebuildable:
capture counts, carry no rows and restore empty. Attribute text/options use the
sensitive retained stream; this adds no subject-erasure claim. Managed catalogue
twins, publication, serving and restore rebuilding remain absent. The experimental
native base-price writer requires the explicit composition described above. No provider, subscription schedule or capability
is enabled by these additions.

## Known limits carried from 0.43.0

Provider and carrier proof is limited to fake clients, scripted adapters and offline fixtures; no live provider or carrier qualification is claimed. The starter still selects sandbox payments. The native payment rail supports the two reference providers through declarative profiles; a third provider needs a declaration plus its adapter. The supplied portable payment composition covers the reference card provider only; the second reference provider has no supplied portable composition. The included warehouse adapter is a reference example. Imports, declarations, package installation and offline certification activate no integration.

Fulfillment retains local reservations and local finished-picking consumption; provider-held reservations, provider-managed consumption, independent splits, standalone pickup-point/locker execution, native label create/void and provider-side cancellation remain unsupported. Labels are PDF only; reference-adapter label reads remain host-owned. Courier pickup has no provider-reaching port and declared support cannot earn full certification. Snapshot-only stock has no movements. Saved preferences require carrier/service strings even when native provider-selected parcels allow nulls. Native overview data requires a host reader.

Historical contacts, reservations, modes, acceptance proofs and arrival facts are not backfilled. Failed or uncertain dispatch and a lost replacement acknowledgement never authorize blind resubmission. Fulfilled parents need an authorized host workflow for replacement dispatch. Replacement creation/dispatch never confirm arrival: record actual delivery; an undelivered replacement remains outstanding. Delivered observations without admitted tracking references retain status evidence but cannot record arrival or alignment. The monotonic clamp never moves a cycle earlier or stacks deliveries.

Intake uses sequential page numbers, not opaque cursors; polling-only providers refuse webhook intake. Empty collections prove no absence. Human holds, terminal provider exceptions and evidence without usable chronology require manual handling. Native reads refuse missing destination/line snapshots. Replaying incomplete webhook transport metadata may replace polling-enriched nullable reference fields. Resolve missing or conflicting historical associations and evidence through authorized recovery; no inferred parcel, chronology or stock is supplied.

Offline certification checks honestly built fixtures and contract results; deliberate accessor, proxy or overridden-intrinsic manipulation to defeat the caller's own certification is outside its threat model. It is not an attestation of durable host behavior. Absence auto-reopen stays off by default and later dispatch requires explicit due-reopen consumption. Refund creation remains separate; refund evidence does not pause or cancel subscription service. Experimental services remain inert until explicitly composed.

Read the [fulfillment execution limits](../reference/limits.md#fulfillment-execution-limits)
and [payment composition boundaries](../reference/limits.md#purchase-composition-boundaries)
for the named refusals and authorized manual paths.
